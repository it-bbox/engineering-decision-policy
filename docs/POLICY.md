# Контракт политики

## 1. Три независимых слоя

**Hard constraints** определяют допустимость решения: поведение, безопасность,
контракты API, доступность, ресурсные SLO и явные требования задачи. Они действуют
для каждого кандидата независимо от профиля и позиции критерия. В demo проверяется
лишь небольшой явно перечисленный контракт; полноценного аудита безопасности нет.

**Ordered quality gates** задают порядок качеств и минимально приемлемые условия.
Каждый уровень имеет одно бинарное значение или одну численную метрику, единицу,
направление улучшения, порог, минимально значимый выигрыш, метод и ограничение вывода.
Если качеству нужны несколько проверок, адаптер должен описать их агрегацию
заранее. Критическое свойство вынеси в отдельное hard constraint. Компенсирующая
взвешенная сумма между уровнями здесь не используется.

**Optimization loop** последовательно ищет допустимые улучшения и фиксирует
checkpoint после каждого принятого изменения. После него hard constraints и
все предыдущие уровни проверяются заново. Итоговый прогон проверяет весь набор.

## 2. Что означает «лексикографический»

Для точной лексикографической задачи сначала находят оптимум f₁ на допустимом
множестве, затем оптимум f₂ среди решений с оптимальным f₁, и так далее. Первое
значимое различие в упорядоченном векторе определяет предпочтение. Большой выигрыш
по позднему критерию не покупает ухудшение раннего.

У coding agent обычно нет ни полного множества реализаций, ни доказательства
оптимальности. Здесь реализуется **ограниченный последовательный поиск с
лексикографическим порядком приоритетов**. Это операционная аппроксимация: агент
сохраняет лучшие достигнутые значения и движется ниже после прохождения порога
и завершения выделенного этапу поиска. «Прошёл порог» и «достиг оптимума» имеют
разный смысл. Алгоритм дополнительно требует неухудшения каждого предыдущего
уровня, даже если другой предыдущий уровень улучшился: это консервативнее общего
лексикографического сравнения двух векторов.

Пусть x — последний принятый checkpoint, x′ — кандидат для уровня k.
Для метрики с направлением max положим gᵢ = fᵢ, с min — gᵢ = −fᵢ.
Кандидат допустим для приёмки, когда:

```text
H(x) = H(x′) = pass
для всех i < k: gateᵢ(x) = gateᵢ(x′) = pass и gᵢ(x′) ≥ gᵢ(x)
gₖ(x′) − gₖ(x) > min_improvementₖ
```

Если текущий порог ещё не достигнут, улучшение можно сохранить как
`ACCEPT_PROGRESS`, но переход ниже закрыт. Бинарный уровень имеет значения
false → true и далее может лишь сохраняться. Равенство даёт `NO_CHANGE`.
Нижние уровни могут ухудшиться, пока их пороги ещё не защищены; если их свойство
обязательно с самого начала, оно должно быть hard constraint.

## 3. Порог, измерение и качество

| Качество | Проверяемое условие | Какой вывод допустим |
|---|---|---|
| Тестируемость | Критичный сценарий проходит с подставной зависимостью | Этот сценарий изолируем; не «вся программа тестируема» |
| Расширяемость | Выбранный способ расширения добавлен без изменения ядра | Поддержан конкретный сценарий изменения |
| Переиспользуемость | Два нужных клиента используют один контракт | Подтверждено использование этими клиентами |
| Читаемость | Метрика сложности + проверка понимания человеком | Метрика — прокси; итог требует контекста |
| Минималистичность | Размер изменения, число сущностей или строк | Размер измерен; смысловая простота не доказана |
| Производительность | Повторный benchmark заданной нагрузки | Известен результат для этой нагрузки и среды |

**Прямое измерение** относится к тому, что фактически наблюдается: число вызовов,
выход теста, время на конкретной машине. **Сценарий** проверяет одно указанное
поведение или изменение. **Прокси** используется как косвенный показатель более
широкого качества. Подсчёт строк объективен как подсчёт, но является прокси
простоты. Цикломатическая сложность, когнитивная сложность и асимптотическая
сложность описывают разные свойства; заменять ими друг друга нельзя.

100% покрытия не доказывает отсутствие ошибок или тестируемость; тестируемость
не равна текущему покрытию. Меньше 50 строк — настраиваемый порог demo, а не
универсальное определение хорошего метода. Адаптер вокруг класса не доказывает
расширяемость во всех направлениях. Специализированная функция может быть
правильным решением без второго потребителя.

## 4. Unknown, шум и конфликты

`measured: false` — измеренный провал бинарного условия. `unknown` — проверка
не выполнена, недоступна или недостаточно надёжна. Unknown не проходит gate.
Отсутствующая метрика также считается неизвестной. Ручную оценку можно записать
как измерение по заранее заданной рубрике, указав reviewer и доказательство;
она сохраняет ограничения этой рубрики и не становится объективной истиной.

Прототип сравнивает конечные числа точно и не допускает ухудшения предыдущих
уровней. `min_improvement` отделяет полезное улучшение от ничтожного, но не задаёт
допуск на регрессию. Это исключает накопительное «сползание» через epsilon.
Для шумного времени адаптер должен проводить повторы, использовать согласованную
статистику и выдавать unknown при неразрешённой неопределённости. Проверку
доверительных интервалов сам сравнитель не реализует.

Если ограничения несовместимы, сохрани последний допустимый checkpoint, назови
конфликт и предложи пересмотр области или требований. Профиль, пороги и исключения
меняются отдельным решением: после изменения политики baseline измеряется заново.
Агент не ослабляет их ради зелёного отчёта.

## 5. Остановка

Бюджет ограничивает число кандидатов и время. Оркестратор/агент ведёт счётчики;
сравнитель одной пары бюджет не контролирует. Если gate достигнут и этап поиска
завершён, допускается перейти ниже без заявления об оптимуме. Если gate не
достигнут, последующие этапы остаются заблокированными. Исчерпанный бюджет означает
завершение поиска, а не удовлетворение критерия. Финальный результат может быть
частичным или заблокированным. Даже все пройденные настроенные проверки
подтверждают только их scope и не гарантируют все инженерные качества.
