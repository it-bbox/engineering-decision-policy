# Методика проверки

## Проверка механизма

Запусти `python3 scripts/run_demo.py` и `python3 -m unittest discover -s tests -v`.
Проверь четыре результата: улучшение изоляции принято; короткий кандидат с
регрессией раннего уровня отклонён; уменьшение работы без ранних регрессий
принято; отсутствующее доказательство обязательного условия не засчитано.
Отдельные тесты проверяют неправильные типы, границы порогов, порядок профиля,
несопоставимые измерения и все предыдущие уровни, включая несоседние.

## Проверка гипотезы на реальных задачах

Гипотеза: явный порядок плюс проверка регрессий повышают соблюдение заданных
приоритетов по сравнению с одной строкой приоритетов и обычным заданием.
Ни выигрыш качества, ни сокращение контекста заранее не утверждаются.

1. До запусков зафиксируй 15–20 задач из целевого репозитория: исправление бага,
   расширение API, повторное использование, упрощение и задача с ресурсным SLO.
   Запиши скрытые тесты и сценарии последующего изменения. Сохрани требования,
   hard constraints, профили и бюджеты; не меняй их после просмотра результатов.
2. Сравни три режима: A — обычное задание; B — то же задание и строка приоритетов;
   C — задание, полный скилл и валидатор. Дай одинаковые инструменты, стартовый
   commit, модель, effort, лимит токенов/времени и правила разрешённых действий.
   Возможный вклад валидатора выдели дополнительным режимом D: полный скилл без него.
3. Выполни не менее трёх повторов в изолированных checkout без переноса контекста.
   Перемешай порядок режимов; держи время измерения benchmark и среду сопоставимыми.
   Сохрани модель/версию, prompt, diff, stdout/stderr, время, стоимость и отчёты.
4. Сначала оцени долю нарушений hard constraints. Среди допустимых решений
   сравни векторы по заранее заданному порядку. Не прячь провал раннего уровня
   за высокой средней оценкой по поздним. Отдельно отчитай unknown и частичные результаты.
5. Два reviewer, не знающие режим, выполняют одинаковые сценарии изменения и
   проверку понимания кода. Измерь время изменения, размер патча, число затронутых
   контрактов, ошибки и расхождения reviewer. Это дополняет численные прокси.
6. Сравни распределения, парные различия по задачам и неопределённость оценок.
   При малой выборке опиши результат как пилотный. Покажи неудачи, стоимость
   инструментария и случаи подгонки метрик, а не только удачные примеры.

## Защита от самообмана

Контролируй удаление тестов, перенос кода за границу scope, минификацию,
фиктивные интерфейсы ради «расширяемости», второй искусственный потребитель и
benchmark, который не представляет нагрузку. Читаемость нельзя объявить
доказанной из-за одного AST-счётчика. Быстрый маленький пример не устанавливает
асимптотику; меньшая сложность Big O не гарантирует меньшую задержку в рабочем диапазоне.

## Критерий решения

Заранее выбери достаточное улучшение соблюдения приоритетов и допустимый рост
стоимости. Принимай политику для проекта, если эксперимент поддерживает этот
критерий без роста нарушений hard constraints. При смешанном результате уточни
scope и повтори эксперимент на новых задачах. Успешная демонстрация механизма
не подтверждает эффективность политики на всех coding agents.

Шаблон итоговой записи: задача; режим; commit; policy hash; бюджет; hard failures;
вектор baseline/candidate; unknown; принятый checkpoint; причина остановки;
стоимость; результат скрытых проверок; результат сценария изменения; reviewer.
